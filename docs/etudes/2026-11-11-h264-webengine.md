# Étude — H.264 dans le cadre web de la release (Qt WebEngine), 2026-11-11

Décision de Jérôme, 2026-11-11 : « inclus h264 directement sans demander de contrats », puis « Oublie mon « fait sans »
installe tout ». Mise à jour le même jour (OA28) : sous Windows, la construction est abandonnée (voir « Windows »). La
release lit H.264 (et AAC) dans les cadres web sur le Mac seulement, et garde le décodeur H.264 du FFmpeg de Qt
Multimedia (installateur Windows, APK).

Le Qt WebEngine officiel (aqt, installateur de Qt) est construit sans `webengine-proprietary-codecs`. Lire H.264 dans un
cadre web demande un Qt WebEngine construit avec cette option, donc une construction de Chromium, faite par nous ou par
un tiers.

## Verdict

| Plateforme | Voie retenue | Où |
|---|---|---|
| Mac | Qt de Homebrew : `qt` 6.12.0 et `qtwebengine` 6.11.2_1, construit avec `-DFEATURE_webengine_proprietary_codecs=ON` | Mac mini, déjà installé, en lecture seule |
| Windows | **Abandonnée (OA28)** : Qt officiel de `C:\Qt\6.12.0\msvc2022_64`, Qt WebEngine sans H.264 ; ces pages se lisent dans le navigateur du système | PC, aucune construction |
| Android | Rien à changer : cadre web = navigateur du système ; FFmpeg de Qt Multimedia gardé | — |

## Sources mesurées

Relevés du 2026-11-11, sauf mention.

### Qt WebEngine 6.12.0 : binaires officiels, sources non publiées
- `download.qt.io/official_releases/qt/6.12/6.12.0/submodules/` liste 43 sous-modules, sans `qtwebengine`. Le lien
  `qtwebengine-everywhere-src-6.12.0.tar.xz` rend 404, sous `official_releases` comme sous `archive`.
- `qt-everywhere-src-6.12.0.tar.xz` pèse 443 394 020 octets, moins que les seules sources de Qt WebEngine 6.11.3
  (580 447 120 octets) : il ne les contient pas.
- `code.qt.io/qt/qtwebengine.git` : tags `v6.12.0-beta1` à `v6.12.0-beta3`, aucun `v6.12.0`. La branche `6.12` s'arrête
  au 2026-08-25 (`d4735ce2`), avec `QT_REPO_MODULE_PRERELEASE_VERSION_SEGMENT "alpha1"` dans `.cmake.conf`. qtbase a, lui,
  le tag `v6.12.0`.
- Le Qt officiel 6.12.0 du cache du runner (aqt) a bien `QtWebEngineCore.framework`, `QT.webenginecore.VERSION = 6.12.0`.

Conséquence : on ne peut pas reconstruire **le** Qt WebEngine 6.12.0 livré par Qt. Une construction 6.12 partirait d'une
bêta ou d'une branche figée. La dernière version publiée, avec sources, est la 6.11.3.

### Homebrew (Mac)
- Installé : `qt` 6.12.0, `qtwebengine` 6.11.2_1 (Chromium 140, `docs/mesures/2026-11-09-cadre-web-webengine.md`).
- Formule (`/opt/homebrew/opt/qtwebengine/.brew/qtwebengine.rb`) : sources `qtwebengine-everywhere-src-6.11.2.tar.xz`,
  `-DFEATURE_webengine_proprietary_codecs=ON`, deux correctifs (SDK macOS 27, ICU 79).
- `qt_lib_webenginecore_private.pri` de Homebrew contient `webengine-proprietary-codecs`.
- Le module annonce `6.12.0` (`Qt6WebEngineCoreConfigVersionImpl.cmake`, `current version 6.12.0` de `otool -L`) : un
  Qt WebEngine 6.11 construit contre qtbase 6.12 prend la version de qtbase. `find_package(Qt6 6.12 … WebEngineQuick)`
  l'accepte.
- Preuve antérieure (T18, 2026-11-10) : `ACTCRAFT H264 w=320 h=240 t=2.362454` depuis le `.dmg` monté.

### Paquets binaires pour Windows, tous écartés
- **conda-forge `qt6-webengine`** 6.11.3 (win-64, 190 Mo) : construit sans codecs. Journal du run 42356427295 du
  feedstock `qt-webengine-feedstock`, job `win_64_` : `Proprietary Codecs ..................... no`,
  `proprietary_codecs=false`. Il dépend en plus de `qt6-main 6.11.3.*`, pas de notre Qt 6.12.0.
- **MSYS2** : aucun paquet `qt6-webengine` (API de recherche, résultat vide). Qt WebEngine ne se construit pas avec MinGW
  (notes de plateforme de Qt).
- **vcpkg** `qtwebengine` : version 6.11.3, option `proprietary-codecs`. C'est une construction depuis les sources, avec
  un qtbase 6.11.3 de vcpkg : elle cumule le coût d'une construction et un autre Qt que le nôtre.
- **PySide6, PyQt6-WebEngine** : ils redistribuent un Qt WebEngine construit par Qt ou par Riverbank, sans codecs (non
  vérifié ici paquet par paquet) ; leur Qt n'est pas non plus le nôtre.
- Aucun binaire Qt 6 avec codecs pour MSVC n'est publié par Qt ni par un tiers trouvé.

### Construction de Qt WebEngine sous Windows : coût
Mesure tierce, la plus proche de notre cas : feedstock conda-forge, run 42356427295, job `win_64_` (2026-11-07),
Qt WebEngine 6.11.3, MSVC, Release, `symbol_level=0`, `use_jumbo_build=false`, `cmake --build -j 4`, runner
`namespace-profile-16cpu-on-win-64` (16 processeurs virtuels ; mémoire non publiée) :
- 35 830 étapes ninja pour Chromium (`[35830/35830] STAMP QtWebEngineCore.stamp`) ;
- compilation de 08:42 à 10:31 UTC, soit **1 h 49**, job complet 1 h 52.

Autres relevés, rapportés par des utilisateurs (non vérifiés ici) :
- forum Qt, Qt 6.6.1, MSVC 2022, parallélisme par défaut sur une machine à beaucoup de cœurs : pics à 112 Go, réussite
  avec 50 Go de RAM et 70 Go de fichier d'échange (https://forum.qt.io/post/810002) ;
- même fil : 8 Go de RAM et 30 Go d'échange suffisent sous Linux ;
- Linux From Scratch : compter environ 1,5 Go de RAM et d'échange par tâche de compilation ;
- forum Qt : 12 Go de RAM ne suffisent pas avec le parallélisme par défaut, même sans jumbo (Qt 6.7.2) ;
- Chromium sous Windows demande « au moins 100 Go libres » sur NTFS (avec symboles et sources complètes).

La mémoire dépend du nombre de compilations en parallèle, pas de la machine. Le PC a 16 Go et 14 cœurs logiques
(Core Ultra 5 125U, `docs/verifications/2026-11-09-tests-intermittents-windows.md`). Par défaut, ninja lancerait 16
compilations : c'est ce qui dépasse 16 Go.

Options qui réduisent le coût :
- `NINJAFLAGS=-j4` : 4 compilations de Chromium à la fois, environ 6 Go au pic de compilation (règle de 1,5 Go par
  tâche). vcpkg règle Chromium par cette variable (`set(ENV{NINJAFLAGS} "-j${VCPKG_CONCURRENCY}")` dans son
  `portfile.cmake`).
- `-DFEATURE_webengine_jumbo_build=OFF` : fichiers fusionnés désactivés, moins de mémoire par compilation (choix de
  conda-forge et de vcpkg).
- `CMAKE_BUILD_TYPE=Release` : `symbol_level=0` chez conda-forge, donc édition de liens sans symboles, la plus légère.
- Fichier d'échange de 32 Go au moins : marge pour l'édition de liens de `Qt6WebEngineCore.dll`.
- ccache, sccache : inutiles pour une construction unique.
- Ni Qt PDF, ni Qt WebEngine Widgets : `-DFEATURE_qtpdf_build=OFF -DFEATURE_qtwebengine_widgets_build=OFF`. Le Qt PDF
  officiel reste celui du Qt copié ; ActCraft n'utilise pas Qt WebEngine Widgets.

Estimation pour le PC, à vérifier au premier essai :
- durée : 16 processeurs virtuels en 1 h 49 ; 4 compilations à la fois sur un processeur portable de 15 W, **6 à 10 h**
  (estimation, non mesurée) ;
- disque : sources 1,03 Go en zip (0,58 Go en tar.xz), environ 4 Go dépliées ; dossier de construction Release sans symboles, 30 à
  50 Go (estimation) ; copie de Qt, environ 5 Go ; prévoir **80 Go libres** ;
- mémoire : 4 compilations, environ 6 Go, plus l'édition de liens ; les sessions Claude du PC doivent rester légères
  pendant la construction.

### Construction sur le Mac mini : écartée
8 Go de RAM, 39 Go libres, 15 Go à garder : 24 Go utilisables, sous le besoin d'une construction de Chromium.
Homebrew fournit déjà le binaire.

## Choix et raisons

### Mac : Homebrew
- Seule voie sans construction ; déjà prouvée (T18).
- Qt WebEngine 6.11.2 sur qtbase 6.12.0 : version publiée par Qt, construite par Homebrew, qui annonce 6.12.0.
- Le bundle Homebrew passait déjà `LICENCES OK` (`docs/mesures/2026-11-09-cadre-web-webengine.md`) : les bibliothèques
  de Homebrew sont listées dans `packaging/autres-autorises.txt`.
- Coûts : Qt de Homebrew est arm64 seul (l'image ne vise que Apple Silicon) ; la release suit la formule installée sur le
  Mac mini, jamais mise à jour par le workflow. Le job vérifie la version de qtbase (6.12.0) et la présence des codecs.
- **Minimum macOS 27** (décision de Jérôme, 2026-11-11, « Go » à « Accepte-t-on macOS 27 au minimum pour le .dmg ? »).
  `macdeployqt` copie dans l'app des bibliothèques de Homebrew construites pour macOS 27 : `otool -l` donne `minos 27.0`
  pour `icu4c@79`, `pcre2` et `double-conversion`, et `minos 14.4` pour QtCore. Sur un macOS plus ancien, l'app
  planterait au lancement. Le paquet déclare donc `LSMinimumSystemVersion` 27.0 (`CMAKE_OSX_DEPLOYMENT_TARGET`, fixé par
  `scripts/paquet-mac.sh`), et `scripts/verifier-minos-mac.sh` refuse un bundle sans cette clé ou dont un binaire exige un
  macOS plus récent. La voie du Qt officiel (`ACTCRAFT_QT_DIR`) garde 14.4, le minimum de Qt 6.12.

### Windows : voie abandonnée (OA28, 2026-11-11)
Jérôme, à la question « Sous Windows, Vimeo et Lumni ne jouent pas sans H.264 dans le cadre web. On construit avant la
release ? » : « Je ne veux pas d'une construction de 6 à 10h ».
- Mesure d'OA26 : avec le Qt officiel, YouTube joue (AV1 + Opus), Vimeo et Lumni ne jouent pas (H.264 + AAC seuls).
- La release Windows prend le Qt officiel, comme la PR #28 : `release.yml` exige un Qt WebEngine **sans** codecs
  propriétaires. Le cadre web ne lit pas H.264 : ces pages se lisent dans le navigateur du système (bouton « Ouvrir dans le
  navigateur » de la PR #30, hors de ce chantier).
- Retirés : `scripts/qtwebengine-h264.ps1` (construction de Qt WebEngine 6.11.3), `essai-installateur.ps1 -H264`, l'avis
  exigé par `verifier-licences.ps1` pour Qt6WebEngineCore et ses deux tests. Le Mac n'est pas touché.

## Licences et brevets
- Qt WebEngine reste `LGPL-3.0-only`, lié dynamiquement. Chromium et son FFmpeg interne (`BSD-3-Clause`, `LGPL-2.1-or-later`)
  sont dans `QtWebEngineCore`, remplaçable par l'utilisateur.
- H.264 et AAC sont couverts par des brevets (licences groupées de Via LA, ex-MPEG LA). Jérôme a décidé de les livrer
  sans contrat de licence (Qt WebEngine du Mac, FFmpeg de Qt Multimedia). `THIRD_PARTY_NOTICES.md` le dit, et le contrôle
  des licences du Mac exige cet avis dans le bundle qui livre Qt WebEngine.

## Mise en place (2026-11-11)

Branche `ci/release-h264`, job `macos` de `release.yml` : Qt de Homebrew en lecture seule, version 6.12.0 exigée,
`webengine-proprietary-codecs` exigé dans `qt_lib_webenginecore_private.pri` de la formule `qtwebengine`.
Relevés sur le Mac mini, code final de la branche, `.dmg` construit par `scripts/paquet-mac.sh` sans `ACTCRAFT_QT_DIR` :

- `scripts/essai-dmg.sh --h264`, depuis l'image montée : `CADRE WEB OK`, `ACTCRAFT H264 w=320 h=240 t=2.082082`,
  `AAC OK`, `ESSAI DMG OK` ;
- contre-épreuve : le même essai sur un `.dmg` fait avec le Qt officiel (aqt) échoue,
  `ACTCRAFT H264 ECHEC code=4` (format non pris en charge) ; l'essai distingue donc les deux Qt WebEngine ;
- minimum macOS (Mac mini, macOS 27.2, 2026-11-11) : `MINOS OK : minimum 27.0` dans `paquet-mac.sh` et dans
  `essai-dmg.sh` (image montée), puis `LICENCES OK`, `DMG OK`, `ESSAI DMG OK` et `ACTCRAFT H264 w=320 h=240 t=2.076362`,
  `AAC OK` ; test `tst_minos_mac` (bundles d'essai : conforme, bibliothèque ou exécutable trop récent, clé absente) ;
  contre-épreuve : avec `LSMinimumSystemVersion` mis à 14.0 en local dans le bundle, le contrôle échoue (`actcraft` et les
  greffons de Qt Positioning à `minos 27.0`), et sans la clé aussi.
### Windows, non joué
- le bloc de `scripts/paquet.ps1` qui exige `QtWebEngineProcess.exe`, `resources/` et
  `translations/qtwebengine_locales/en-US.pak` (les locales sont copiées depuis Qt, car `windeployqt --no-translations` les
  saute) ; il vaut aussi pour le Qt officiel, et `paquet.ps1` s'arrête avec un message clair s'il manque un fichier.
